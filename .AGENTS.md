# .AGENTS.md — coding rules for agents

How agents write code in this repository. Process rules (milestones, gates, reviews) live in
[`AGENTS.md`](AGENTS.md); this file is about the code itself. Loaded into OpenCode sessions via
`instructions` in `opencode.jsonc`.

The spec (`docs/details.md`) and the decisions log (`docs/decisions.md`) still win on content.
These rules govern *how* the code is written, not *what* it does.

## Comments and documentation

1. **Comments are allowed only where the code is not self-explanatory.** If a rename or a small
   restructure makes a comment unnecessary, do that instead of writing the comment.
2. Comments explain **why**, never **what**. `// clamp so the fit loop cannot exceed 1.0` is a
   comment; `// add one to the counter` is noise.
3. No commented-out code, no "remember this" notes, no changelog narration — git history is the
   changelog. Delete stale comments when the code they describe changes.
4. Doc comments (`///`) describe the contract (invariants, errors, units, panics), not the
   implementation. Every public item gets one line; expand only when the contract is subtle.
   Inside `src/` private items need doc comments only when their purpose is not obvious.
5. `TODO`/`FIXME` must name a concrete plan or milestone (`TODO(M2): …`) — never open-ended.
6. Never invent APIs or facts. Verify against docs.rs for the exact pinned version, or a local
   compile experiment, before using anything (spec §13.6).

## Rust idioms

7. `cargo fmt` owns formatting — never hand-format, never debate it. Clippy with
   `-D warnings` must stay clean; fix the code, don't suppress, unless the lint is wrong
   (then `#[allow]` with a comment explaining why).
8. Prefer iterators and combinators over index loops. Prefer `?` over `match`-ladders that just
   propagate. Early returns beat nested conditionals; keep functions short and single-purpose.
9. Match on enums exhaustively; never downcast through `as` or stringify to branch. Avoid
   boolean parameters — use a named enum or two functions instead.
10. Make illegal states unrepresentable: newtypes over primitive strings for domain values,
    closed enums over open string sets, builders or constructors that guarantee invariants.
11. Derive what you use, nothing more; implement traits explicitly when the derived behavior
    would be wrong (e.g. semantic equality vs. structural).
12. Borrow before owning: `&str` over `String`, `&[T]` over `Vec<T>` in parameters. `.clone()`
    only with a reason (test code is exempt). No `unsafe` — if something seems to require it,
    stop and reconsider the design; the spec has no unsafe code.
13. Public API surface stays minimal: expose what commands and tests need, keep the rest
    private. Prefer free functions over single-impl structs; add traits only with a second
    implementation in sight.

## Errors and failures

14. No `unwrap()`/`expect()` outside tests and `main` startup; anything else needs a comment
    stating the invariant that makes it safe (spec §13.8).
15. Errors are typed enums (`thiserror`), carry context (path, field name), and never swallow
    details. Convert rich types to user-facing strings only at the CLI boundary.
16. Every user-facing error must have a test that triggers it and asserts on the message
    (spec §13.9). Prefer asserting on stable substrings, not the full text.

## Testing

17. Unit tests live next to the code (`#[cfg(test)] mod tests`); end-to-end behavior gets
    integration tests in `tests/`. Test names read as sentences describing behavior, not the
    method name.
18. Tests are deterministic: no sleeps, no network, no ordering assumptions. Isolate
    filesystem state in unique temp directories.
19. Assert on behavior and observable messages, not internals. One behavior per test; if a
    test name needs "and", split it.
20. Bug fixes arrive with the failing test that reproduces the bug, fixed in the same commit.
21. **The code is tested, aiming for 100% line coverage.** Before declaring work done, check
    coverage (`cargo llvm-cov`, or the equivalent available at the time) and close the gaps
    it reports. Code that genuinely cannot be reached from tests (internal invariants,
    crash-only paths) must carry a comment stating why, like the `unwrap()` rule — that is
    the only acceptable exception. Coverage is a floor, not a substitute: 100% covered
    lines still need behavioral assertions (rule 19), not tests that merely execute code.

## Dependencies

22. Every new crate needs a one-sentence justification in the PR (spec §2). Prefer std. If one
    small function is all you need, write it (and test it) instead of adding a dependency.
23. Pin versions exactly for the rendering stack (`=`) and normally elsewhere; update pins
    deliberately, never as a side effect of other work.

## Structure and change discipline

24. Keep related code together: a module's tests, helpers, and types live in that module.
    Don't spread one feature across files without reason; don't add "utils" dumping grounds.
25. Comments/doc comments in a module must stay accurate when you change that module — stale
    docs are bugs in the docs.
26. Match surrounding style first; apply these rules fully to code you write anew. Fix
    unrelated style only where you already touch the code — no drive-by refactors.
27. No scope creep: implement the spec/plan step, nothing more. Ideas beyond the spec go in
    the PR description or `docs/decisions.md` as a proposal.
28. Sequential reasoning tasks (parsers, fit loops, render pipelines): check termination,
    determinism, and edge cases explicitly — empty input, zero, overflow, repeated runs.
29. Concurrency and I/O: operations that produce user-visible files must be atomic (write temp
    → rename) and deterministic (same input → same bytes).
